# Business rules in a pure domain package; thin routes → services → repos

The backend is layered. Thin Fastify routes validate input, call one service and map the result to a DTO. Per-use-case services (`apps/api/src/modules/<feature>/service.ts`) load data, call domain, persist, and own the transaction. `packages/db` repos handle persistence. Every decision rule (matching, Relevance, pricing, bid placement checks, Scoring, winner selection) lives in `packages/domain`, which is pure: no I/O, no clock (`now` is a parameter), deterministic. The rule of thumb: anything that needs the DB or the clock goes in a service, and any decision made from given values goes in domain.

The Closing use case lives only in the worker (`apps/worker/src/close-campaigns.ts`), since the api never closes Campaigns. The api may still run `closeCampaign` read-only to show an Advertiser the provisional "if it closed now" outcome of an Open Campaign; it never persists that result. Bid placement and Closing call the same domain functions, so the snapshot that gets persisted can't drift from what Closing reads. Rule failures come back as `Result<T, E>`; only broken invariants throw. Explanations are structured `Factor[]` (never prose) and web renders the copy. Scoring is stamped with `SCORING_VERSION`. The skeleton ships a placeholder `closeCampaign` (zero Score, decided tie-break, greedy within Budget) that Map 2 replaces.
